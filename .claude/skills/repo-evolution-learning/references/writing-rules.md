# 中文简明表达规则（spec §7 中文适配）

ASD-STE100 是英文技术写作标准。中文报告采用其简明表达原则，不声明严格合规。官方参考：https://www.asd-ste100.org/STE_faq.html

## 可检查规则

写 `narrative` 正文时逐条遵守：

1. 一句话只表达一个主要意思。
2. 先描述可观察的行为，再解释机制；术语不要在机制之前出现。
3. 首次出现技术术语时，给出简短中文解释。
4. 同一个概念始终使用同一个名称，不换近义词。
5. 明确写出「谁做了什么，导致什么结果」，保留完整主语。
6. 结论旁保留必要边界（例：「旧文件可用，但不能证明本次成功」）。
7. 不用抽象结论替代具体变化。禁用词表见 `evidence-rules.md`；另不用「增强可靠性」「提升稳定性」等空泛说法，改为具体动作，例：「把失败状态写入文件，让后续检查能发现它」。
8. 正文约 800–1200 个中文字。只保留 1 个主要教训 + 1 个次要取舍 + 1 个小实验。这是产品设计目标，不是 STE 标准要求。

## 5 问叙事结构

`narrative` 正文按五个问题组织，每题一段：

1. 出了什么问题？（可观察行为）
2. 根本原因是什么？（机制）
3. 作者怎么修？（改动 + 代价）
4. 效果如何？（证据 + 边界）
5. 我能学到什么？（迁移条件 + 小实验）

`headline` 用一句话点明「一个具体的修复复盘」，例如「Archify：生成失败，为什么检查仍然通过？」，避免读者误以为覆盖了整个项目发展过程。

## 对照示例

| 原表达 | 简化表达 |
|---|---|
| 把失败持久化为显式 provenance | 生成失败后，把失败状态写入文件，让后续检查能发现它 |
| 自动 stale-lock 回收存在 check-to-unlink 窗口 | 一个进程确认锁已失效后，另一个进程可能已经替换了锁。此时删除锁，会误删新锁 |
| 保持 last-good 产物的向后兼容 | 生成失败时保留上一次成功的文件，但标明它不是本次结果 |
| 该项目通过架构演进显著提升了系统鲁棒性 | 作者增加了任务检查点。任务失败后，系统可以从检查点恢复。测试覆盖了进程中断场景。生产恢复效果尚未确认 |

## 校验分工

- 校验器（`validate`）检查结构与禁用表达；`narrative` 必填字段由模型 `min_length` 强制。
- 你（skill）复核主语、含义、证据与条件、字数，以及「一个教训 + 一个取舍 + 一个小实验」的收敛。
